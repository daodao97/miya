# 委派任务的访问级别（审批统一第 3 步）

状态：实施步骤 1 到 4 已完成，单元测试通过，待隔离实例实测（2026-11-15）。前两步见 `docs/action-review.md`（自动化的访问级别、审查与许可；共享的命令分类 `internal/approval`；项目范围的许可）。

## Abstract / 摘要

`start_task` 新增可选参数 `access`（`read`、`edit`）。设了它的委派任务，接收方对话按这个级别运行，它冒出的审批请求由 Miya 当场答复，不再挂着等一个可能没人看的卡片。对外动作不在接收方做：Miya 拒绝它，记在任务上，随完成通知交回发起委派的对话，由那里在人的监督下处理。

## Background / 背景

- 委派任务的权限现在是 `permissionForThread(target)`：新对话取窗口当前的全局选择（`internal/controller/delegation_controller.go` 的 `prepareDelegation`），已有对话取它自己的选择。
- 结果是两头不讨好：窗口选「手动」时，接收方的每个审批都变成卡片，发起方在 `wait_task` 里干等；选「完全放开」时，接收方什么都能做，包括推送和发消息，而发起委派的 Agent 和人都没有看到。
- 自动化已经有一套现成的东西：访问级别到 Claude/Codex 权限的映射（`internal/agent/policy` 的 `Read`、`Edit`），无人值守答复，命令分类（`internal/approval`），项目范围的许可。

## Design / 设计

### 参数

`start_task` 的 `access`：

| 值 | 接收方 | Claude Code | Codex |
| --- | --- | --- | --- |
| 不填 | 同现在：已有对话用它自己的选择，新对话用窗口的选择 | 同现在 | 同现在 |
| `read` | 只读 | `manual`，Miya 只放行只读命令 | 沙箱 `read-only` |
| `edit` | 可以改工作区文件、跑本地命令、本地提交 | `acceptEdits` | 沙箱 `workspace-write`，不联网 |

没有 `external`：对外动作交回发起方处理（见下），不在委派里排审查。

### 只能收窄，不能放宽

委派不能成为绕过权限的路子：发起方自己改文件都要人批准时，不能让一个委派去改。

- `read`：总是允许。
- `edit`：发起方的权限是「帮我审批」「完全放开」或 `edit`（例如发起方本身是 `edit` 的自动化或委派）时允许；发起方是「手动」或 `read` 时拒绝，返回 `ACCESS_DENIED`，说明要么让人在窗口里放宽，要么用 `read` 委派、自己动手改。
- `access` 只用于新开的对话；同时给了 `thread_id` 时返回 `INVALID_ARGUMENT`。已有对话有它自己的权限选择，人可能正在用它，临时改了再恢复不值得这份状态。

### 答复接收方的审批请求

接收方对话的审批请求到达时，若它属于一个设了 `access` 的进行中任务（对话的权限是 `read` 或 `edit`，且协作里有一个在这个对话里运行的任务；任务结束后人在这个对话里继续聊，请求照旧等人）：

1. **项目许可。** 命令判为对外、并且项目范围的许可覆盖它的类（第 2 步）：放行。
2. **本地动作。** `edit`：工作区内的 `Edit`、`Write` 等和判为本地的 `Bash` 放行。`read`：只读命令放行，其余拒绝。
3. **对外动作。** 拒绝。拒绝信息告诉 Agent：这个委派不允许对外动作，不要换方式绕过，先做完不依赖它的部分，并在最后的回复里写明需要发起方做什么。Codex 发来的审批一律按对外处理（同自动化）。

被拒绝的动作记在任务上（`refused`，最多 20 条），`read_task` 和完成通知里都列出来，不靠接收方的 Agent 记得说。发起方的对话是普通对话，人在场：它可以自己执行这些动作，走正常的审批卡片。

### 不变的部分

- 不填 `access` 时行为完全不变。
- 完成通知走现有的委派投递（`coordinator.deliverPending`）。
- 分类器不是安全边界，这一点同 `docs/action-review.md`。Codex 一侧的不联网沙箱是更可靠的边界。

## Rationale / 理由与取舍

- **为什么对外动作交回发起方，而不是像自动化那样排审查。** 委派一定有一个发起它的对话，那个对话本来就在人的监督下；把动作交回去，人在同一个地方用同一种卡片批准，不需要第二套审查队列。自动化没有这样的上级对话，才需要审查记录。
- **为什么不填时不改默认。** 现在依赖委派继承「完全放开」跑通的工作流会突然开始被拒绝。Miya 的说明里会建议发起方填 `access`。
- **为什么 `edit` 要看发起方。** 否则一个手动审批的对话可以借委派让另一个 Agent 不经批准地改文件。

## Implementation / 实施步骤

1. `internal/approval`：把「这个请求是不是本地的、叫什么」的判断（现在是 `automation.classify`、`within`、`bashCommand`）移进来，自动化和委派共用。
2. `start_task` 加 `access`：校验，按发起方收窄，`Effective.Policy` 设为 `read` 或 `edit`，任务记下级别。
3. 控制器：接收方的审批请求按上面的规则答复，被拒绝的动作记到任务上。
4. `read_task`、完成通知列出被拒绝的动作；MCP 说明建议填 `access`。
5. 测试；隔离实例里实测：`edit` 委派推送被拒，发起方收到通知后自己推送并出卡片。

### 验收

| 场景 | 验收标准 |
| --- | --- |
| `read` 委派试图改文件 | 被拒绝，任务记录写明；任务不卡住 |
| `edit` 委派改文件、跑测试 | 不出卡片，直接完成 |
| `edit` 委派执行 `git push` | 被拒绝；完成通知列出这条动作 |
| 项目许可覆盖 `git push` 时的 `edit` 委派 | 推送放行 |
| 手动审批的对话发起 `edit` 委派 | `ACCESS_DENIED` |
| 不填 `access` | 行为和现在完全一样 |
