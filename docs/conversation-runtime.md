## Abstract / 摘要

我们为每个对话建立结构化的运行态，记录原生后台任务、可核验的系统进程、监听端点以及关联证据。Codex、Claude Code 和后续 Agent 通过各自适配器提供事实，Miya 的通用层负责归属、状态合并、存活核验和服务发现。桌面、手机和 Agent 的只读查询使用同一份数据。Web 列表是运行态的一种视图。

最重要的承诺是：**只有已证明属于该对话的进程，才能出现在「本对话服务」里。** 不完整的观察保留为未知，项目目录扫描只提供另行标注的候选。Claude 与 Codex 同期交付；能力不足时明确降级。

## Background / 背景与动机

改造前，[internal/runtime/web/discovery.go](../internal/runtime/web/discovery.go) 通过监听进程的工作目录判断项目归属，再用 HTTP HEAD 探测端口。这能找到项目中的网站，却回答不了「它由哪个对话启动、当前是否仍由那个 Agent 持有」。

例如同一项目的对话 A 启动 `npm run dev`，对话 B 启动 API。两者工作目录相同。当前实现会在两个对话里显示同一组端口；进程切换到其他目录后又可能被漏掉。这是归属依据不足，继续增加目录规则解决不了。

项目代码已经区分原生对话和运行进程，但尚未把这些信息统一起来：

- [ThreadRef](../internal/chat/model/ref.go) 有稳定的桌面来源、Agent 和原生会话标识；本机临时 `Thread.ID` 不适合作为持久归属键。
- [chat_events.go](../internal/controller/chat_events.go) 接收 Codex 工具事件；此前 [codex.Item](../internal/agent/codex/native/types.go) 未保留命令项的 `cwd`、`processId`。
- [Claude 适配器](../internal/agent/claude/native/client.go) 接收工具和系统事件，但 [agentTracker](../internal/agent/claude/native/agents.go) 原来主要围绕子 Agent；本次补齐了后台工作集合与 shell 的生命周期。
- 窗口、手机与 Agent 的实际执行均由桌面后台负责，运行态也应由这个后台持有。

## Design / 设计

### 运行态是一份事实记录，能够支持多种视图

我们新增独立的 `internal/runtime` 模块。它不依赖 Codex、Claude 协议或手机 UI，由 controller 协调 Agent 适配器和系统观察器。适配能力挂到现有 `agentBackend` 注册机制；扩展 Agent 时一起扩展 `ThreadRef` 的后端校验，避免新的运行态模块另建一套后端名单。

```text
Codex 适配器 ──┐
Claude 适配器 ─┼─ 原生任务与执行证据 ─→ 对话运行态 ─→ 后台运行视图
其他适配器 ───┘                         │        ├→ Web 服务视图
系统观察器 ──── 进程身份与监听端点 ──────┘        └→ Agent 只读查询
```

这份记录先覆盖任务、进程和端点。日志正文继续留在现有工具消息或原生任务输出里，运行态只保存来源引用和必要摘要，避免复制整段聊天。它也不承担用户偏好、项目知识等长期记忆。

### 原生任务、系统进程和服务分别建模

| 对象 | 关键事实 | 可以缺失的关联 |
| --- | --- | --- |
| 对话 | 桌面来源、Agent、原生 session ID | 未取得原生 ID 的草稿暂不建立运行态 |
| 后台工作 | 原生 task/process 标识、运行批次、命令或说明、状态、工具调用来源 | 可以知道后台工作存在，但不知道 OS PID |
| 系统进程 | 主机、系统启动标识、PID、进程启动标识、父子关系、观察时间 | 可以确认属于对话，但不知道具体属于哪个工具调用 |
| 服务端点 | 进程身份、实际监听地址、端口、协议、探测状态 | HTTP 响应成功不等于一定有可用的网站首页 |
| 归属证据 | 原生关联或已观察到的进程父子关联、来源、时间、有效范围 | 命令文本、工作目录和输出中的 URL 只能作为线索 |

原生 `processId`、Claude `task_id` 与 OS PID 使用不同字段。即使某个标识只包含数字，也不能把它直接转换成系统进程号。

原生任务用 Agent 会话内的任务标识和运行批次区分；SDK 提供 `run_id` 时保留。系统进程用主机、系统启动标识、PID 和启动标识区分。只有 PID 相同不足以证明还是原进程。

创建者和使用者也分开记录。对话 B 访问 A 启动的服务，不会因此成为这个服务的创建者；输出中提到一个地址也不会自动产生所有权。

### 通用层消费标准化事件，适配器声明自己能证明什么

以下接口表达模块边界，具体字段在实现时收敛，不把某个 Agent 的原生类型暴露给 UI：

```go
type Adapter interface {
    Capabilities() Capabilities
    Reconcile(context.Context, SessionKey) (Snapshot, error)
}

// 原生流由现有 controller 接收，适配器将其转换后送入 Store。
func (s *Store) Apply(Event)
func (s *Store) ApplySnapshot(Snapshot)
func (s *Store) Read(SessionKey) View
```

`Capabilities` 分别声明任务事件、任务全量快照、原生 PID、独占会话进程根、重连恢复和存活依赖。支持任务事件不代表支持 PID 映射，支持读取也不代表允许停止。

`Snapshot` 必须声明会话、执行连接批次、覆盖的对象集合及其完整性。完整的任务快照只替换该来源的任务集合，不能顺带删除尚在运行的系统进程。分页未取完、超时或缺少支持均不能生成「完整空集合」。

同一原生连接上的事件按接收顺序合并；重连增加批次，旧批次不能覆盖新状态。同一任务的新运行使用新身份。支持版本号或运行标识的适配器利用这些字段拒绝迟到事件。

### Codex 和 Claude 分别接入，再通过同一套契约验收

| 数据来源 | Codex | Claude Code |
| --- | --- | --- |
| 对话内工具执行 | command item、输出与终端交互事件 | Bash tool use/result、原生任务事件 |
| 后台工作的当前集合 | `thread/backgroundTerminals/list`，取完分页后替换 | `background_tasks_changed`，按事件携带的完整集合替换 |
| 系统进程归属 | 原生后台终端提供的 `osPid`，以及同用户监听进程继承的 `CODEX_THREAD_ID`，继续核验系统身份和子进程 | Miya 启动的独占会话 CLI 根进程及已观察到的后代；有直接 PID 证据时补充 |
| 信息不足 | 保留原生后台工作；未提供 PID 时不猜 Web 端口 | 保留原生后台工作；脱离进程树且未被捕获的进程标为未知 |
| 重连恢复 | 重新查询原生后台终端；不为查看而执行 resume | 清理连接批次状态，按原生协议恢复快照；无法恢复时保留未知 |

Codex 的客户端是多个对话共用的。不能把整个 app-server 的所有后代分给某个对话，必须从原生后台终端或进程实际继承的精确对话标识建立归属。

Claude 的后台任务事件区分 Bash 和 Agent，并提供集合变更快照；这些记录没有承诺提供 OS PID。官方协议据此支持任务归属，系统进程关联仍须另行核验。[Claude SDK 后台任务事件](https://code.claude.com/docs/en/agent-sdk/typescript#sdkbackgroundtaskschangedmessage)

Claude 的适配器需要补齐 `task_type`、运行批次和全量任务事件。`TaskCreated`/`TaskCompleted` 的任务清单语义不能替代后台 shell 生命周期。现有 tool result 中「启动成功」也不表示该后台工作已经结束。

优先使用现有原生事件流。Hooks 仅作为确有缺项且版本已验证时的补充，局部接入 Miya 启动的会话，不修改用户全局配置，不改写 shell 命令或审批结果。Hook 中的 session、工具调用和任务信息也须由适配器核验，不能因为来自一段文本就当成系统进程身份。[Claude Hooks](https://code.claude.com/docs/en/hooks)

### 系统观察只核验有归属证据的进程

系统观察器接受已核验的原生 PID 或独占会话进程根，采集进程身份、后代与监听端点。实现可以复用当前 `lsof` 解析，但归属筛选改用进程证据，工作目录只用于展示和项目候选。

当进程树仍完整时，我们记录后代的完整身份及其会话来源。后代随后被托管给其他父进程，只要身份一致，已记录的归属仍成立。若进程在首次观察前就脱离，原生协议没有直接 PID，且无法核验对话环境标识，我们无法证明它属于该对话。短间隔观察只能减少漏报，不能承诺捕获所有 detach。

观察窗口在相关工具执行和后台工作变化时打开，进程表读取在主机内合并；有已知后台工作时采用有上限的后台核验。打开运行信息或 Web 列表时立即刷新。初始预算为相关事件合并 200 毫秒、活跃观察间隔 1 秒、闲置后台核验间隔 10 秒；实际开销在实现验收中测量，不能把这些预算当作已达到的结果。没有相关任务和已知进程时停止周期观察。

不读取全机进程环境变量。为恢复在首次观察前就已脱离的 Codex 服务，仅对同用户 TCP 监听候选读取 `CODEX_THREAD_ID`，精确匹配当前对话；其他环境内容不进入运行态、日志或持久化文件。读取前后的主机、启动批次、PID、进程启动时间必须一致，防止 PID 复用。macOS 从 `kern.procargs2` 跳过可执行路径和参数后读取环境，Linux 从 `/proc/<pid>/environ` 读取。标识缺失或不可读时不猜归属。也不以「某段命令执行期间新增了一个进程」证明归属；同一项目内并发执行会使这种推断串线。

### Web 服务是端点的实时核验结果

```text
已归属的进程 → 监听地址/端口 → HTTP 探测 → 本对话 Web 列表
```

HTTP HEAD 只访问本机端点，不跟随外部跳转。已核验归属的端点支持回环地址及电脑网卡实际持有的数字 IP；局域网其他机器的地址不能成为代理目标。非回环代理必须带绑定进程身份和监听端点的运行态 token，桌面在拨号前重新检查本机地址和端点。非 HTTP 端口仍可显示在后台运行详情中。HTTPS、自定义域名、容器和远程执行需要各自的端点解析能力；不能把日志中的任意 URL 直接变成代理目标。

同端口的 IPv4/IPv6 监听保留实际地址及进程身份。点击打开前重新核验身份和端点，避免页面停留期间原服务退出、端口被其他对话占用后打开错误的网站。探测失败与进程退出分别展示；404 或认证要求不等于进程已结束。

### 生命周期同时描述任务、进程和观察是否可靠

原生任务结束、工具调用返回、模型结束一轮回答、系统进程退出，是不同的事实。通用层不把它们互相替代。

Claude 当前的退出路径在原生 agent/schedule 都不活跃时关闭输入，并在超时后取消进程组。新增后台 shell 支持时，必须同时修正这个持有条件：已经证实仍有后台工作，就不能因主回复完成而提前清理它。界面上模型回合可以空闲，后台工作继续运行。

后台升级也需要区分进程是否依赖宿主存活：退出宿主会终止的会话工作应延后升级并显示原因；已核验且独立存活的进程不因历史归属而一律阻塞升级。首版不自动停止后台资源来让更新生效，遵守现有[安装流程](install-and-upgrade.md)。

断线表示观察失联。Miya 保存最后观察时间和来源，显示未知或待核验。后台重启后先核验主机启动标识和进程启动身份，再恢复显示。没有重验的历史记录不直接显示为运行中；也不能因没有新事件就判为已退出。

### 桌面、手机和 Agent 使用同一个只读视图

对话增加「后台运行」详情，展示后台工作、命令来源、进程及其端点。现有「Web 服务」直接过滤这份运行态，不再维护手机专用的另一套归属逻辑。桌面和手机查看同一份数据，普通会话列表广播只携带必要计数与修订号。

对话里的默认范围是本对话。首页提供项目总览：聚合已归属的对话资源，并把目录发现的未归属服务单独标成项目候选。新建对话还没有原生身份时，也不把项目候选当成它自己启动的资源。

Agent 可以通过绑定当前 `SessionKey` 的只读查询取得相同信息，了解此前启动的服务。后续发送请求可附带有变化的简短运行态摘要，完整日志按需读取；不把运行态反复写入共享记忆或整段塞进提示词。

这次设计只提供观察和预览。停止、重启、输入命令属于后续独立能力，要使用 Agent/系统适配器声明的控制能力，不能从通用任务 ID 拼出 `kill` 命令。

### 保存来源和有限历史，保持查询与更新有边界

运行态存放在桌面后台自己的版本化存储中，以稳定对话标识索引；不混入现有只保留侧栏元数据的 thread cache。持久化内容包括原生任务身份、已核验进程身份、归属证据和最后观察时间。写入合并，退出历史限量保留，恢复时重新核验。

命令可能包含凭据。展示和持久化使用脱敏、限长的命令摘要，原始工具输出沿用现有记录。查询须校验桌面来源、项目可见性、Agent 和原生 session ID；旧临时数字 ID 不能作为其他会话的回退键。

## Rationale / 理由与取舍

我们选择维护结构化运行态，而不是让模型总结一份「背景信息」。运行状态随时会变，模型总结既可能过期，也不能证明 PID、端口或进程归属。模型可以解释事实，不能代替采集事实。

我们保留 Agent 适配层，而不是只围绕 Codex 后台终端建模。Codex 原生 PID 信息更丰富，Claude 的事件集合恢复方式不同。强迫它们提供相同的原生字段会造成伪造归属；通用层应统一含义和可核验状态，允许某些关联缺失。

我们选择事件采集与快照核对结合。只看工具输出会把示例地址、启动失败或旧日志当成存活服务；只靠事件又可能漏掉断线期间的变化。完整快照修正任务集合，系统观察修正进程和端点，但两者不相互冒充。

我们没有把目录扫描升级为主要归属方法，也没有采用简单的启动前后进程差集。它们对并发对话都无法给出排他证据。目录扫描的保留价值是帮助用户找未归属的项目候选。

代价是需要两套原生适配、进程身份存储和后台观察。收益是同一层可以支持非 Web 的后台命令、日志任务和后续 Agent；UI 无需为每种工具重复推断。确实拿不到证据的场景会漏报归属，我们接受明确的未知，避免静默串线。

## Compatibility / 兼容性

这是增量能力，但对话里的列表含义会改变：从项目目录候选变为有对话归属证据的资源。项目候选仍可在项目总览查看，手动输入端口继续可用。

新增独立运行态能力协商和版本化查询。旧手机继续使用已有项目服务接口；新手机连旧后台时显示项目范围或更新提示，不把旧列表标成「本对话」。原有 Tailcat 通道和 HTTP 代理继续复用，不改变 v5 已有消息含义。

旧对话不推测历史所有权。能从原生快照或已保存的有效进程证据恢复时补齐；其余保留为候选或未知。Miya 自有终端将来可作为另一个明确的执行来源接入，不能自动分配给当前打开的聊天。

## Implementation / 实现与过渡

实施分四步，Codex 和 Claude 均在首版验收范围内：

1. 建立通用模型、合并器和进程身份存储，先用两种 Agent 的协议 fixture 验证事件/快照语义。核心模块不得引用任一 Agent 协议包。
2. 接入 Codex 后台终端分页与 Claude 后台 shell/任务集合事件，记录会话独占 CLI 根身份，修正 Claude 后台工作存活条件。补版本缺失和失联降级，不改用户全局 Hooks。
3. 实现进程关系与端点观察，把现有 lsof、HTTP 探测下沉为通用观察器。通过身份和来源筛选，覆盖进程退出、PID/端口复用、已观察后重挂父进程以及共享服务的使用关系。
4. 桌面与手机接入统一的后台运行/Web 视图，提供 Agent 只读查询。项目目录发现保留在项目总览。通过两端功能验证后再按已有流程安装。

验收必须证明同一套行为在两种 Agent 下成立：

| 场景 | 验收结果 |
| --- | --- |
| 同一项目两个对话并行启动不同服务 | 两个对话只显示各自已归属服务 |
| 后台命令并非 Web | 后台运行详情可见，Web 视图不列入 |
| 对话回复完成，后台 Bash 继续 | 回合状态与后台工作状态独立，服务不因回复完成被提前清理 |
| 原生任务 ID 恰为数字 | 不将其当作 OS PID |
| 多页原生快照中途失败 | 保留未知/旧观察，不发布完整空集合 |
| 原生快照和增量事件重复、迟到或跨运行批次 | 不重复、不复活旧任务、不串会话 |
| 进程已观察后脱离父进程 | 身份一致时保留归属，身份变化时失效 |
| 原生任务存在，但无可靠 PID | 后台工作可见，Web 关联保持未知 |
| 同端口不同地址，或端口被其他进程复用 | 列表和打开行为均核验实际端点与进程身份 |
| 后台重启、电脑重启、手机换桌面 | 旧缓存先标为待核验，稳定会话和进程身份不串线 |
| 服务由 A 创建，B 仅访问 | 创建来源保留 A，使用关系不会改写来源 |
| 旧端、无系统观察权限、原生协议不支持 | 能明确显示能力边界，手动预览继续可用 |

已完成通用模块 `internal/runtime`、现有 `agentBackend.Runtime` 适配接口、原生任务快照和独立会话进程根、身份与端点核验、版本化运行态文件、桌面后台运行面板、手机后台详情和 Web 视图，以及绑定当前调用对话的只读 `runtime_info` 工具。

验证覆盖标准化存储、原生协议分页与集合完整性、迟到事件、重挂父进程、PID/端口复用、失联和持久化恢复、只读查询来源、界面导航，以及同目录两个 Codex/Claude 对话的进程隔离。双 Agent 隔离测试采用合成原生协议进程并启动真实 HTTP 服务；没有调用在线模型。并发检查覆盖运行态与两种客户端。模型摘要自动注入仍是后续可选优化，当前通过只读工具按需获取。

当前系统进程观察支持 macOS、Linux；其他系统明确返回无法核验。任务详情可以保留，但不会据此猜测服务。Codex 脱离进程只在保留精确对话环境标识且仍有 TCP 监听时补充归属；标识缺失且此前未被观察到的进程仍无法归属。
