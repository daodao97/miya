# 为 Miya 增加可追溯、跨 Agent 共享的记忆

作者：Codex；评审修订：Claude  
更新日期：2026-11-05
状态：阶段 1a、1b、2 已实现并通过自动化验收；已验证真实 Claude 提炼与新 Codex 会话自动召回；阶段 3 待实施，长期使用质量尚待观察
讨论依据：本次 Alma 记忆实现分析与 Miya 设计讨论，以及随后的设计评审。评审以[本文件](memory.md)为入口；目前没有关联的 Issue 或 PR。

## Abstract / 摘要

我们在 Miya 后台服务中增加共享记忆。用户明确保存的信息，以及由回合筛选的稳定偏好、明确决策和可复用经验，进入本地存储。自动提炼不保存施工流水，也不向会话插入卡片；统一在记忆管理页查看和纠正。Codex 和 Claude Code 使用同一份记忆，桌面与手机通过已有服务通道访问。

最重要的承诺是：记忆有来源、可纠正、可忘记，用户能直接看到存了什么，且记忆处理失败不阻止正常聊天。

交付分四步，每步独立可用：

1. **1a 显式记忆与主动查询**：存储、MCP 工具、桌面管理界面。Agent 需要时自己调用 `search_memory`，不改发送管线。
2. **1b 自动注入**：发送时按会话增量附带相关记忆，需要把用户原文与注入上下文分离。
3. **2 自动提炼**：回合完成后由受限的结构化调用生成候选，再由确定性代码校验写入。
4. **3 混合检索与整理**：embedding 与关键词融合、过期归档。

第一阶段（1a、1b）使用 JSON 文件和本地关键词检索，不增加数据库或模型服务依赖，不能描述为语义检索。

## Background / 背景与动机

用户在一个 Claude Code 会话中确定了某个项目背景，再新开 Codex 会话时，往往需要重新说明。用户可以显式引用旧会话，但必须先知道哪段记录值得带过去。记忆要解决的是：在已有来源基础上，补上少量与新问题相关的背景。

例如，用户在会话 A 中说「这周先不动手机端协议，等手机版发布」，之后在会话 B 中要求调整服务消息格式。Miya 可以召回这条临时约束并带上来源，过了有效期后不再召回。另一个会话中的「正在修复断线重连」属于进展，修复完成后应当更新，不能长期保持为当前状态。

像「后台升级必须等任务空闲」这类长期、团队共享的约束，已经写在仓库的 `AGENTS.md` 中，不应再由记忆重复保存，分工见下文。

现有代码提供了以下接入基础：

- [agent.go](../agent.go) 的 `submit` / `submitExpanded` 统一路由、排队和发送请求，两个后端通过 `agentBackend` 适配；`sendRequest` 已有 `Text` 与结构化 `Parts`。
- [handoff.go](../handoff.go) 已能从规范化消息生成有界上下文；[会话引用设计](thread-references.md) 已定义来源、后端、会话身份和发送快照，`ThreadRef` 位于 [thread_reference.go](../thread_reference.go)。
- [mcp_host.go](../mcp_host.go) 已能把 MCP 调用解析到发起会话及其项目（见「MCP 调用者身份」）。
- [automation_parse.go](../automation_parse.go) 已通过独立 Agent 调用获取结构化结果：Claude 使用 `--tools ""` 禁用工具；Codex 使用 `exec --sandbox read-only`，仍可执行命令和读取磁盘，不等于禁用工具。

这些能力尚不构成记忆系统。我们还需要定义哪些信息可以保存、怎样纠正、什么时候注入，以及如何避免后台旧任务把删除的信息写回来。

本设计借鉴 Alma 的选择性提炼、主动召回和来源记录。Alma 的分析来自本机安装包静态检查，没有证明其提取准确率。本文中的存储、作用域和发布顺序是 Miya 的设计选择。

## Design / 设计

### 记忆分成偏好、事实和进展，采用不同更新方式

| 类型 | 示例 | 作用域与更新方式 |
| --- | --- | --- |
| 用户偏好 `preference` | 偏好中文解释、常用工具 | 用户明确选择用户级作用域后跨项目使用；纠正时按 ID 替代旧版本 |
| 项目事实 `fact` | 个人做出的决策、临时约束、已验证经验 | 默认仅在当前项目使用；保留来源，按 ID 和版本替代 |
| 项目进展 `progress` | 用户明确要求保存的目标、阻塞和交接信息 | 只通过显式记忆或管理界面保存；按任务标识更新，结束或过期后停止召回 |

项目可以同时有多个任务。进展按目标或任务标识保存，不能用整个项目唯一的一条「下一步」互相覆盖。无法归属任务的摘要只供该来源会话参考，不自动替代其他会话的进展。

记忆是历史背景。当前用户指令、当前项目明确约定和实际文件状态优先于它。来源不明的推测不能成为长期事实；助手声称「测试通过」只能先记录为助手报告，只有对应工具结果才能支持「已验证通过」。

### 记忆不替代 AGENTS.md / CLAUDE.md

项目文件可审阅、可提交、对团队和所有工具生效；记忆是本机、个人、可能过期的背景。二者按下表分工：

| 适合记忆 | 适合项目文件 |
| --- | --- |
| 个人偏好、本机环境细节 | 团队共享的长期约束和流程 |
| 带有效期的临时约束 | 构建、安装、审批等硬性规则 |
| 任务进展、未成文的阶段性决定 | 已经稳定、希望所有协作者遵守的决定 |

记忆管理界面为项目事实提供「提升到项目文件」操作：生成建议文本，由用户确认目标文件和措辞后写入，原记忆随后标记为已提升并停止召回。Miya 不自动改写 `AGENTS.md`、`CLAUDE.md`。召回时若某条记忆与项目文件内容重复，以项目文件为准；第一阶段不做自动去重检测，作为试用检查项。

### 后台服务拥有数据，Agent 和客户端通过接口访问

`internal/memory/` 负责作用域、存储、校验、检索、版本和删除规则。外层适配器负责读取 Miya 消息、调用提取器、构造 Agent 输入和响应 MCP 请求。这个包不依赖窗口，也不自己启动 Codex 或 Claude。

```mermaid
flowchart LR
    Input[用户消息] --> Recall[服务按作用域召回]
    Recall --> Delta[按会话计算增量]
    Delta --> Snapshot[保存本轮注入快照]
    Snapshot --> Agent[Codex 或 Claude 执行]
    Agent --> End[规范化回合完成事件]
    End --> Job[持久化提取任务]
    Job --> Extract[受限结构化提取]
    Extract --> Validate[校验来源与版本]
    Validate --> Store[后台单写者更新记忆]
    Store --> Recall
```

图中提取路径属于第二阶段。后台以外的窗口、手机和 MCP 工具进程不直接写文件。远程手机使用其当前连接的桌面数据实例；第一版不提供多台桌面之间的记忆同步。`MIYA_SERVICE=0` 时关闭自动注入和自动提取，不额外启动另一个写入者。

### 一条记忆保留稳定身份、证据和生命周期

下列是设计层的数据组成，最终 Go 字段命名可以在实现时细化：

| 数据 | 含义 |
| --- | --- |
| `id`、`version` | 随机稳定 ID、每次修改递增的版本 |
| `scope`、`projectKey`、`kind` | 用户级或项目级作用域、规范项目标识、偏好/事实/进展 |
| `content`、`taskKey` | 简短正文；进展另带任务标识 |
| `sources`、`evidenceKind` | 来源消息、必要的原文摘录和证据类别，如用户声明、助手报告、工具结果 |
| `observedAt`、`validUntil` | 原信息的时间、可选有效期；保存日期不作为事件发生日期 |
| `state`、`supersedes` | `active` / `superseded` / `forgotten` / `expired` / `promoted`，以及替代的旧条目 |
| `createdAt`、`updatedAt` | 本地管理时间，与原信息时间区分 |

**不设自动生成的逻辑键。** 「同一事实」无法由 Agent 自填的键或文本相似度稳定判定：同一约束换个说法就会得到不同的键，键不稳定时替代会退化成追加。因此修改一律指向具体条目：

- 第一阶段：纠正必须先 `search_memory` 找到条目，再按 `id` 和 `version` 替代；管理界面中的编辑同理。
- 第二阶段：提取器只能从服务提供的候选旧条目 ID 中选择替代目标，不能自由生成标识；选不出确定目标时只能新增或返回待核实。

来源会话直接复用 `ThreadRef{Source, Backend, SessionID}`，不依赖标题或运行时 `Thread.ID`。消息优先使用后端稳定消息 ID；没有可复用 ID 时，保存持久化的回合标识和消息定位摘要，标明定位能力有限，不能把正文哈希单独当作消息身份。

同一条记忆可以有多个来源。会话分支保留各自的 `ThreadRef`；从分支观察到的新结论需要经过合并规则，不把旧会话的身份自动改到新分支上。

项目标识由规范化的绝对工作区路径生成，既保存摘要键，也保存路径供定位；存在时解析符号链接，同名目录不会共享记忆。移动目录后需要显式迁移归属，第一版不按项目名或 Git remote 自动合并。不同 worktree 默认是不同作用域，代价见「理由与取舍」。

### 第一版按作用域保存 JSON，所有修改经过单写者

```text
serviceDir()/memory/
  user.json
  projects/<project-key>.json
```

每个作用域文件包含格式版本、作用域修订号、记忆条目、删除标记、提取任务状态和有界的注入记录。用户级文件与项目级文件各自提交；自动提取只写当前项目，不能产生跨文件更新。显式提升到用户级作为独立操作处理。

服务在内存中按作用域串行修改。提交时写同目录唯一临时文件，完成写入和刷新后原子替换目标文件，再发布新的内存修订。保存失败不报告成功，也不让只存在于内存的新事实参与下一轮召回。目录权限为 0700，文件权限为 0600。

缺失文件表示没有记忆。损坏文件、未知格式版本或作用域不匹配表示该作用域不可用：保留原文件、记录错误，停止写入它，聊天继续；不能把损坏文件当空库覆盖。

显式记住、纠正和忘记优先于后台任务。第二阶段的提取任务持久化输入消息定位、内容摘要、目标作用域修订和处理状态；同一时刻只有一个提取调用运行；恢复后重试前重新校验来源和修订，不持久化无限增长的完整对话副本。

### 第一阶段 1a：Agent 主动查询，用户直接管理

1a 不改 `sendRequest`，也不自动注入。MCP 工具描述告诉 Agent：开始涉及项目背景的任务时可调用 `search_memory`。这一步验证两件事：跨 Agent 共享是否真有价值，以及存储、来源、删除规则是否成立。

桌面端提供记忆管理界面，是「可纠正、可忘记」承诺的主要入口，不能只依赖 Agent 代为操作：

- 按项目和用户级列出记忆，显示类型、正文、来源会话（可跳转）、时间、有效期和状态。
- 支持编辑（生成新版本）、设定有效期、忘记、提升到用户级、提升到项目文件。
- 只有用户通过 Agent 明确请求记住时，在对应会话中显示带作用域的确认与撤销入口。自动提炼和管理界面操作只刷新记忆库，不新增会话消息；旧版自动插入的卡片不再呈现在时间线。

服务无法验证 Agent 调用 `remember` 时是否真有用户明确要求。可见提示和一键撤销比校验 Agent 自填参数更可靠。手机端第一阶段只读查看，编辑留到协议能力协商完成后。

### 第一阶段 1b：消息真正执行时召回，按会话增量注入

自动记忆与显式会话引用有不同的时间语义：

- 显式引用继续遵守现有约定，保留提交时选定的来源快照。
- 自动记忆在实际开始执行时召回；消息在队列中等待时不固定它。
- 合并队列后，为合并后的新回合召回一次。立即引导同样经过公共上下文准备流程，不能绕开作用域与删除规则。
- 同一次发送的网络重试使用同一请求标识和记忆快照，避免重复注入或更换输入；用户重新编辑发送则是新请求。

实现上扩展 `sendRequest` 的内部表示，把用户原文、结构化 `Parts`、显式引用快照、自动记忆上下文分开保存。窗口显示、标题生成、草稿返还、排队编辑、文件提及解析和后续提取都使用用户原文。只有后端适配器构造输入时组合上下文，不能反复向 `req.Text` 追加隐藏正文。

**按会话增量注入。** Codex 会话和 Claude 保活进程会累积历史；每轮重复注入同一条记忆既浪费额度，也会被模型当作反复强调。服务按会话（`ThreadRef`）记录已注入的 `id@version` 集合：

- 会话首轮注入召回结果。
- 之后只注入本轮新召回、且该会话尚未见过的条目。
- 已注入条目出现新版本、被忘记或过期时，只发送一次纠正或失效说明。
- 后端会话重建上下文（例如 Codex 压缩历史或 Claude 新进程续接）后，视为新的首轮。若无法可靠感知，退化为每 N 轮重新注入一次，N 初定 20。

召回先限定作用域，再排序：当前项目有效条目，加上项目设置允许的用户偏好。去掉被替代、已忘记、已提升和已过期条目；对进展检查任务身份和时效。每次注入最多 5 条，正文和来源提示总量不超过 4,000 个 Unicode 字符，超出时按整条裁剪。条数和长度是初始预算，后续以测量调整。

第一阶段使用规范化词项、标识符、类型和时间排序，支持中英文混合输入；当前任务进展有单独的匹配权重。查询不清楚时返回少量或空结果，不把所有项目资料一并注入。检索只读本地内存，不发起前置模型调用。

每次实际注入记录选中的 ID、版本、作用域修订、正文快照和请求标识，便于诊断「当时为什么知道这个」。本地诊断快照每会话最多保留 20 轮、最长 30 天，仅针对仍在重试的请求临时保留必要输入。超过期限后明确表示诊断记录已清理，不影响后端自己的原始会话历史。

给 Agent 的记忆块说明历史时间、来源、可能过期，以及当前要求优先。它不授予工具权限，不覆盖审批策略。原有 Agent 会话已经包含历史输入，Miya 不重写整段历史；失效说明不能保证模型彻底忽略旧事实。

### 第二阶段：回合完成后先生成候选，再由确定性代码决定如何保存

Codex 的 `turn/completed` 和 Claude 的顶层 `result` 转换成公共完成事件。Claude 可以保活，进程退出不是唯一完成信号；子 Agent 的结果也不是顶层回合结束。UI 的 `Busy` 变化不能单独触发提取。

事件捕获需要在排队消息开始下一轮前，固定完成回合的来源和消息范围。幂等键使用来源实例、后端会话和持久化回合标识，重复帧、重连或历史加载不会再次生成同一任务。

自动提取只处理启用它的项目里成功完成的前台用户回合。停止、失败、历史恢复、MCP 控制消息、自动化校验反馈和记忆提取调用本身不触发提取。用户在这些会话中仍可显式记住经过确认的信息。自动化如何贡献项目进展留到后续扩展。

输入以完成回合为单位，包括本轮真实用户消息、最终回答、必要的已完成工具证据，以及服务按相关度选出的候选旧条目（带 ID）。不能固定截取最后四条消息，以免丢失多次引导；也不能在工具输出里任意截一个片段后声称覆盖了全部执行结果。提取输入上限初定 16,000 字符，优先保留用户要求、最终结论和证据定位；超过范围的候选必须回到可核验来源，不能填补省略部分。

提取器输出 `add`、`supersede`、`forget` 候选，每项附候选类别、长期保留类别 `retention`、来源消息 ID 和原文依据；`supersede`、`forget` 的目标必须是输入中给出的旧条目 ID。一次最多接受 3 项操作，其中最多新增 1 条；同一主题优先纠正现有结论，无长期价值时返回空数组。`retention` 只接受稳定偏好 `preference`、用户明确的项目决策 `decision`、可复用经验 `lesson`。语义价值仍由提炼模型判断；类别声明不能代替证据校验。

Go 代码逐项检查：作用域是否允许、来源是否属于本轮、引用摘录是否存在、证据类别是否支持结论、目标 ID 和版本是否仍有效。网页、附件、工具文本和注入的旧记忆不作为用户新指令。正文相同可直接去重；语义相近但不能确定是同一事实时先保留为待核实候选，在管理界面中提示，不自动覆盖。

自动写入的记忆只在记忆管理页显示，可编辑和忘记，不生成聊天卡片。助手报告和 `progress` 不再自动保存，安装、测试、界面微调、快捷键现状以及可直接查代码或文档得知的信息也不应自动记忆。显式记忆仍允许用户主动保留进展。此策略只约束新的自动写入，不批量删除已有记忆。

**提取后端。** 复用 `automation_parse.go` 的进程管理和结构化结果解析，另外提供 memory 提取 schema、提示词、超时与受限运行目录。提取调用只接收服务给定的数据，不连接 Miya MCP，不续接主会话，不写工作区。

- Claude：`-p` 加 `--tools ""` 可以满足数据访问边界，需要适配器测试确认 MCP 也未加载。
- Codex：只使用 `exec --sandbox read-only` 仍可执行命令、读取磁盘，不满足边界。现已增加专用受限 CLI 适配器：关闭已安装 CLI 注册的可选能力、操作工具、MCP、技能和 hooks，在临时空目录运行并校验事件及结构化结果。

提炼 Agent 可在项目记忆设置中独立选择 **Codex** 或 **Claude Code**，使用该 CLI 的默认模型及认证环境。旧配置未指定时继续使用 Claude Code。所选 Agent 不可用时禁止开启新的自动提炼，不静默切换到另一个 Agent；显式记忆与本地召回继续工作。

**超时与队列。** `claude -p` 加 schema 的冷启动和 16,000 字符输入可能接近或超过 30 秒。超时值不在设计阶段拍定：第二阶段开始前先测量 p50 / p95，再分别设置启动超时和生成超时；总截止时间初定 90 秒，最多重试一次。队列合计最多保留 100 个待处理回合，满时停止接受新自动任务并记录跳过，不丢用户原对话，也不阻塞新发送。服务调度循环只处理状态和不可变消息副本，模型调用与文件 I/O 不在主调度循环中等待。调用会使用用户现有 Agent 额度，不承诺额外免费的后台能力。

### 纠正、忘记和过期必须处理正在运行的旧任务

替代总是指向具体 `id` 和预期 `version`；版本已变化时提交失败，调用方需重新查询。显式纠正优先于后台作业：慢作业在提交时发现目标版本或作用域修订已变化，必须重新校验，不能覆盖较新的明确纠正。

**冲突检测属于第二阶段。** 判断两条记忆语义矛盾需要模型参与，第一阶段的关键词检索做不到。第一阶段只保证版本竞争正确；两条看似矛盾的记忆会同时存在，由用户在管理界面处理。第二阶段由提取器在候选旧条目中指出矛盾，确定性代码将双方标记为冲突、停止自动召回，等待用户选择。

忘记先提交删除标记并推进作用域修订，再移除正文、向量和 Miya 自有注入快照中的副本。删除标记只保留阻止旧来源回灌所需的 ID、摘要、来源定位和修订，不继续存原文。引用已忘记来源、旧事实版本或旧候选的作业不得写回。新的用户明确「重新记住」可以建立新的条目。

自动提取的 `forget` 必须能对上本轮用户明确的删除或纠正要求，并指定输入中给出的真实旧条目；模型不能因为一段工具文本就删除记忆。不确定删除对象时返回匹配项供澄清，不扩大到整个主题或全部项目。

清理多个文件时，删除标记是访问屏障：清理未完成或重启恢复时，不再返回关联旧快照。删除后不能复用尚未发出的旧请求快照；若后端已接收本轮，说明其输入中已包含旧背景，并在后续回合提供一次失效说明，不以重试名义重新发送。

忘记不能删除 Codex / Claude 已有历史、系统备份或用户自行复制的文件。文档、界面和工具返回值必须区分「Miya 不再保存和召回」与「所有副本已删除」。

**有效期。** 第一阶段只有显式记忆，`validUntil` 由用户或管理界面设定，未设定即长期有效；项目进展默认 7 天后退出自动召回。第二阶段提取器可以建议有效期（例如「这周先不动」），由确定性代码换算为具体日期并在提示中展示。稳定事实和明确偏好不按固定天数删除。失效过滤是确定性的，后台闲时清理；后续合并与归档不默认新增一个必须全天运行的凌晨任务。

### MCP 工具让 Agent 主动补查和修改

| MCP 工具 | 行为和边界 |
| --- | --- |
| `search_memory` | 默认查当前项目与项目设置允许的用户偏好；返回 ID、版本、内容、来源、时间和冲突状态。工具不允许读取其他项目 |
| `remember` | 保存用户要求记住的内容及来源；默认项目级。用户级需要当前用户在对话中明确要求，并在提示中标明作用域。修改已有条目时须带 `id` 和 `version` |
| `forget_memory` | 忘记精确 ID 和版本；先按查询查找再精确删除。只允许修改调用者当前可访问的作用域 |

对话可描述「记住」「纠正」「忘记」，Agent 再调用工具；MCP 描述负责给出契约，不承诺纯文本每次都能被模型正确理解。提取器、管理界面与 MCP 工具使用同一个合并和校验入口，避免多套修改逻辑。

### MCP 调用者身份是第一阶段的前置条件

工具进程通过现有 MCP → 服务通道访问。服务不相信客户端声明的项目路径、用户身份或消息来源。当前机制（[mcp_host.go](../mcp_host.go) 的 `mcpCaller`）如下：

- MCP 进程传来的工作区参数不受信任，因为 Codex 的一个 app-server 服务所有项目。
- 服务在所有项目的会话中查找「状态为进行中、名称匹配」的 Miya 工具调用，取开始时间最晚的那一个作为调用者，再由该会话推出项目。
- 找不到时返回 `mcpCallerUnknown`，MCP 进程有限次重试。

这对现有只读工具够用，但对写操作不够：两个会话同时调用 `remember` 时，按「最晚开始」会把其中一次归到错误的会话和项目，产生跨项目写入。实现 1a 前必须满足：

1. 写工具（`remember`、`forget_memory`）匹配到多于一个候选调用时，用调用参数与消息中记录的工具参数比对消歧；仍不唯一则失败并让 Agent 重试，不按时间猜测。
2. 没有确定调用会话时失败，不回退到全局作用域或 MCP 进程声明的工作区。
3. 适配器测试覆盖：两个项目的会话并发调用同名写工具，各自写入正确作用域。

### 开关

第一阶段提供项目级使用开关、自动注入开关、自动提取开关（第二阶段生效）和当前会话禁用标记。自动注入和自动提取在已有安装中默认关闭；显式记忆工具和管理界面默认可用。禁用当前会话同时停止自动注入和自动提取，不影响该会话既有历史。用户级偏好是否参与每个项目由项目设置控制。

## Rationale / 理由与取舍

| 决策 | 选择理由与放弃的备选项 |
| --- | --- |
| 由宿主服务共享记忆 | Codex 和 Claude 已有自己的会话与潜在记忆机制，Miya 补充来源一致的共享背景。只依赖单个 Agent 的私有笔记，跨 Agent 时无法给出统一的纠正与删除语义 |
| 记忆与项目文件分工 | 团队约束放在可审阅、可提交的项目文件中更可靠。全部塞进记忆会与 `AGENTS.md` 重复甚至冲突，且只对本机生效 |
| 先做 Agent 主动查询（1a），再做自动注入（1b） | 自动注入要改造发送管线，覆盖 steer、队列、重试、编辑和 Claude 保活，风险最大。先用主动查询低成本验证共享价值和存储规则 |
| 按会话增量注入 | 常驻会话会累积历史，每轮全量注入浪费额度并造成重复强调。代价是需要按会话记录已注入集合，并处理后端重建上下文的情况 |
| 修改指向具体 ID，不设逻辑键 | 自动生成的逻辑键无法稳定识别「同一事实」，替代会退化为追加。代价是纠正需要先查询，由界面和工具承担这一步 |
| 第一阶段提供管理界面 | 服务无法验证 Agent 是否真的收到用户要求。可见提示和一键撤销是更可靠的防误记手段 |
| JSON 先落地，存储接口可替换 | 符合现有持久化方式，先验证小规模记忆的收益。全文件改写和单写者有规模上限；若每作用域达到数千条或持续超过 5 MB，应测量写入延迟并评估 SQLite，而非继续叠加文件索引 |
| 事实与索引分离 | embedding 模型可以更换或不可用，事实、来源和删除规则不能因此丢失。第一版加入向量会同时引入模型配置、索引迁移和构建兼容成本 |
| 自动提取默认项目级 | 同一句技术偏好在不同项目可能适用范围不同。全部升级为全局记忆，会带来跨项目误用和更难解释的删除行为 |
| worktree 默认隔离 | 避免路径相近的不同检出互相污染。代价是并行使用多个 worktree 的用户会分别积累记忆；后续可考虑以 `git rev-parse --git-common-dir` 作为可选共享键 |
| 自动记忆在执行时选择 | 排队期间记忆可能更新。显式引用保留用户提交时的选择；自动记忆负责执行时的相关背景，二者分别记录 |
| 提炼 Agent 按项目独立选择 | Codex 与 Claude Code 共用校验和提交入口，各自使用受限适配器及已有 CLI 认证；旧配置保留 Claude 默认，避免升级后切换额度来源 |
| 进展按任务覆盖，事实按版本替代 | 把所有完成情况追加成永久事实，会使旧状态长期压过新状态。只维护一个项目摘要又会让多个并发会话互相覆盖 |
| 先不接屏幕记录和复杂结晶 | 本需求针对 Miya 对话中的项目连续性。屏幕活动需要独立的数据来源和权限设计；反复出现的话题自动升级为技能也需要单独的执行权限边界 |

我们不把自然语言记忆当作执行策略。安装、审批、工作区限制等硬性要求继续由现有约定和程序执行，记忆不能自行扩大权限。

## Compatibility / 兼容性

该功能按开关增量加入，不迁移或重写 Agent 原生记录，不自动导入 Alma、Codex 或 Claude 的私有记忆，也不自动改写项目的 `AGENTS.md`、`CLAUDE.md`；提升到项目文件只在用户确认后执行。旧对话没有记忆元数据时按原方式发送。

协议中增加记忆设置和诊断字段时，按现有桌面服务与手机协议的版本约定处理能力协商。老客户端不提供管理入口；服务不能把完整记忆库附到常规状态广播中。对外只在明确的查询、设置或发送响应里返回必要数据。

打开自动注入后，Agent 输入会增加少量背景；自动提取还会消耗调用额度。这些是实际行为变化，不能仅以「新增字段」描述为零成本。关闭后停止新注入和新任务，取消未提交的自动任务，已有存储保留供查看或显式清理。

记忆作业不要求后台永久驻留。现有服务升级需要空闲退出时，停止领取新作业；正在运行的提取调用最多等到其截止时间，之后取消，把可恢复任务保存在磁盘，再允许切换。重启后按幂等键和当前修订恢复，不强杀正在执行用户任务的后台。

## Implementation / 实现与过渡

### 实施前必须保持的不变量

以下条款散见于正文，集中列出以便直接转成测试：

1. 只有后台服务写记忆文件；保存失败不报告成功，不让未落盘的修改参与召回。
2. 损坏或未知格式的作用域文件不被覆盖。
3. 项目记忆只在本项目召回和修改；MCP 写操作的调用者必须唯一确定。
4. 用户原文与注入上下文分开保存，显示、标题、草稿、编辑和提取只使用原文。
5. 同一请求的重试复用同一注入快照；同一会话不重复注入已见过的 `id@version`。
6. 修改必须指定 `id` 和预期 `version`；版本不符则失败。
7. 删除标记先于正文清理生效；引用已忘记内容的作业和快照不得写回或复用。
8. 记忆处理的任何失败都不阻止正常发送。

### 阶段 1a 实施记录（2026-11-02）

当前交付可独立使用的显式记忆，不启动自动注入、自动提炼或 embedding 调用。

- `internal/memory/` 实现规范项目作用域、JSON 格式校验、单写者原子提交、版本竞争、遗忘屏障与中英文关键词查询。损坏、未知版本及作用域不匹配的文件保留原样并拒绝写入；未成功落盘的修改不进入查询结果。项目进展需要 `task_key`，默认有效期七天。
- `memory_mcp.go` 注册 `search_memory`、`remember`、`forget_memory`。记忆的读取和写入均按真实工具消息参数确定唯一调用者，不能用客户端工作区或最新开始时间猜测。两个项目同时调用同名工具、两种后端原始事件保留参数和完全相同参数的歧义拒绝均有测试。保存时服务定位本轮用户消息中的原文摘录；仍无法从自然语言判断用户真实意图，因此保留可见提示和撤销入口。
- 桌面入口为 **Settings → 记忆**：项目/用户偏好列表、来源会话、时间、有效期、状态、编辑、忘记、项目偏好提升到用户级，以及项目事实提升到 `AGENTS.md` / `CLAUDE.md`。项目文件操作先预览最终文本，再由用户确认写入；文件或版本已变化时拒绝旧预览。用户级提升是两个独立作用域提交，部分成功会明确返回已创建的用户记忆 ID。
- 记忆查询默认只包含当前项目；用户偏好需在项目设置显式启用。管理界面始终可用，停用项目记忆工具不会删除已有内容。此处记录的是 1a 交付状态，自动功能开关与会话禁用标记随后在 1b/2 接入。
- 会话提示只保存 ID、版本和作用域，正文按需读取；更新/遗忘后通过修订通知使窗口和手机缓存失效。提示不额外持久化正文。原生后端重新加载历史时，运行期间插入的提示可能不再显示；已保存的条目与来源仍可在管理页查看和忘记。
- 手机侧边栏新增 **共享记忆**，通过能力字段 `memory` 请求只读列表；没有手机写入接口。正常状态广播仅携带能力与修订，不携带记忆库。旧桌面显示升级提示，切换桌面会清空该页缓存。
- 所有记忆文件 I/O 在服务调度循环外执行；已接受的操作计入忙碌状态，后台空闲升级不会截断提交。`MIYA_SERVICE=0` 不创建记忆写入者。

1a 的自动化验收覆盖持久化失败、损坏文件保护、项目隔离、版本竞争、全版本正文/摘录遗忘及重启、过期与任务过滤、跨 Agent 查询、MCP 参数消歧、项目文件预览/并发修改保护、桌面明暗主题、可见撤销提示、手机只读与桌面切换。后续真实链路及性能结果见下节。

### 阶段 1b / 2 实施与验证记录（2026-11-02）

- `memory_context.go` 与 `internal/memory/context.go` 在后端实际执行前准备记忆，覆盖 Codex 普通发送与引导、Claude 新进程、保活发送与引导。队列提交时不固定自动记忆，显式引用仍保留提交时快照。自动上下文只在构造后端输入时附加，不修改 `sendRequest.Text`、结构化 `Parts`、用户气泡或标题；两种后端的历史重载会移除自动记忆块。
- 按会话增量注入，新版本、遗忘和过期只通知一次；上下文重建或压缩后重放，每 20 次准备保守重放一次。每次最多五项、总量不超过 4000 个 Unicode 字符。重试复用驻内存快照，发送前复查版本、有效期及开关，失效则丢弃旧块，聊天继续。
- **诊断与原设计的取舍：** 磁盘只记录请求 ID、会话、条目 ID/版本/状态和送达状态，不保存第二份记忆正文。每会话最多 20 条、保留 30 天。因此遗忘不会留下诊断正文副本；代价是旧版本被纠正或忘记后，不能还原当时的完整注入文字，跨进程重试也不恢复旧正文快照。
- `memory_extract.go` 从 Codex `turn/completed` 与 Claude 顶层成功 `result` 固定本轮真实用户消息、最后回复和能够完整容纳的已完成工具证据，再异步入队。停止、失败、子 Agent、历史加载、自动化、MCP 委派和原生任务控制不触发提炼。无法确定项目任务身份的进展只供来源会话使用；原生目标按会话和目标正文摘要区分。
- `internal/memory/jobs.go` 持久化有界证据和来源定位，最多 100 个未完成任务，一次只运行一个调用。输入最多 16000 字符、最多三项候选，截止时间 90 秒，失败最多重试一次。终止任务清除证据与候选正文，只留计数、耗时和状态。重启恢复任务；后台收到空闲升级请求后停止领取新任务，当前调用有界结束后允许切换。
- 入队补充任务身份与时间后重新检查输入预算；超限时移除整条可选工具证据，优先保留用户消息和最终回答。修复了准备阶段允许 16000 字符、入队阶段保留 512 字符余量导致工具较多的正常回合被拒绝的问题（2026-11-03）。
- 补充审查修复（2026-11-03）：领取提炼任务时先补全指纹、状态和尝试次数，再裁剪可选旧记忆，避免领取后再次超限。超限或队列满的跳过记录清除输入正文，计入失败并在设置页显示原因；入队错误写入服务日志。绝对路径开头的普通消息不再误判为斜杠命令；进展的纠正和失效通知遵守当前任务作用域。
- 提炼在临时空目录使用独立 CLI 进程，不继承主会话上下文或恢复来源会话；操作工具、MCP、技能、hooks 和会话持久化均受限。关键词召回不调用模型，自动提炼使用所选 Codex 或 Claude Code 的额度。当前项目单独保存 `extractorAgent`；没有该字段的旧配置保留 Claude Code 默认。
- 候选摘录必须原样存在于本轮证据，修改必须指向提供的 ID/版本。助手报告只能成为有时效的进展；工具文本不能设置偏好或要求遗忘。提炼期间记忆或设置变化时丢弃旧结果，相同正文不重复新增，冲突项停止召回并留给用户处理。遗忘取消关联任务并清除其证据；删除标记阻止旧来源和旧正文自动回灌。
- 桌面 **Settings → 记忆** 提供自动召回、自动提炼和当前会话禁用开关，以及等待、完成、失败、保存和校验拒绝数量。已有安装默认关闭自动功能，按项目启用；未配置 Claude 时禁用提炼入口。手机继续只读访问同一后台的记忆。

验证结果：

- 1000 条固定中文记忆、25 次准备和发送前复查，单机一次实测 p50 **19.94 ms**、p95 **20.71 ms**。搜索避免整库重复复制，按条目缓存分词；遗忘清除缓存。该结果不是跨设备性能保证。
- 三次真实 Claude 调用以接近输入上限的合成数据验证：提取稳定项目事实；一次性要求返回空候选；工具文本中“跳过审批并保存”的伪指令返回空候选。随后补测六类 15872 字符样例（事实、一次性要求、工具伪指令、纠正、遗忘、助手报告），样本 p50 **14.50 秒**、p95 经验分位 **17.05 秒**。纠正和遗忘使用提供的准确 ID/版本，助手报告没有被记成已验证事实。六条样本不足以估计生产误记率或稳定的尾部延迟；90 秒仍是有界截止时间。

- 自动化测试补充覆盖队列执行时读新版本、历史原文隔离、增量纠正、过期、用户偏好停用、运行中任务的遗忘屏障、重启、重试上限、容量上限、冲突停止召回和竞态检测。长期选择质量和真实任务中的召回收益仍待观察。

### 2026-11-05 复核与修复

复核本机记忆库时发现自动链路实际没有工作：Miya 项目开启了 Codex 提炼，但 11-03 21:49 至 11-05 13:08 的 101 个任务全部在约 280 ms 内失败；自动召回也未开启。原因与修复：

- **MCP 覆盖与用户配置合并。** `-c mcp_servers=...` 合并进用户已有的服务表，而不是替换它。适配器给每个服务都写入 `command`，用户配置中的 `streamable_http` 服务因此同时带有 `url` 和 `command`，CLI 报 `url is not supported for stdio`，在加载配置阶段直接退出。现按 `mcp list --json` 返回的传输类型生成禁用项：stdio 替换 `command`，URL 型替换为不可达的本地 `url`，两者都设 `enabled=false`。原有的探测测试只配置了 stdio 陷阱，已补充 URL 型陷阱。
- **列出 MCP 时的网络访问。** `codex mcp list --json` 会对每个 URL 型服务做 OAuth 发现请求，在隔离之前就访问了用户配置的远程端点。该调用现在使用指向不可达地址的代理环境，列表只读取本地配置；探测测试断言 URL 型陷阱没有收到任何请求。
- **失败原因不可见。** 适配器丢弃 stderr，任务只记录本地化的通用文案，服务日志没有记录。现在 CLI 错误保留为有界的单行摘要：写入任务的 `detail` 字段、设置页的提炼状态和 `service.log`，不包含提炼输入。
- **重复失败的熔断。** 同一提炼 Agent 连续 3 个任务实际运行失败后，30 分钟内不再入队新回合，设置页显示恢复时间；之后放行一个任务作为探测，成功后恢复。入队前的跳过记录（队列满、超限）不计入；切换提炼 Agent 不继承暂停。
- **设置写到了文件系统根目录。** 从 Finder 启动且未指定工作区时，窗口的 `cwd` 为 `/`，设置页把开关保存到了 `/` 作用域，对实际项目中的对话不生效。服务现在拒绝把根目录作为项目作用域，设置页提示先打开项目；用户偏好分页不受影响。
- **普通 Claude Code 回合从不提炼。** 记忆钩子以线程 `Status` 为空作为回合成功的条件，但非保活回合收到顶层 `result` 时 `Status` 仍是“运行中”，要到进程退出才清空；只有带后台任务、子 Agent 或定时任务的保活回合会入队。本机记录中 Claude Code 只有 11-04 的 5 个任务，此后没有再入队。现在由 `result` 分支直接判定成功（未停止、未报错、非空结果、不在等待子 Agent），回归测试在旧代码上失败、修复后通过。

修复后使用本机真实 Codex 配置（含 URL 型服务）运行真实提炼：稳定事实提炼出 1 条，一次性要求和工具伪指令返回空，单次耗时约 25–31 秒，高于此前 Claude 样本的 14.5 秒 p50，仍在 90 秒截止时间内。`TestDiscoverProjectWebServicesWithRealListeners` 在干净的 `HEAD` 上同样失败，与本次修改无关。

## Appendix / 后续需要依据验证结果决定的扩展

- **项目移动与 worktree 共享。** 第一版显式隔离；后续如要共享，先设计可追溯的作用域映射和迁移，可评估以 Git common dir 为可选共享键，不能按相同仓库名自动共享。

- **自动提取调用成本。** 先复用已配置 Agent；第二阶段用耗时、额度和质量数据决定是否增加独立的小模型配置。
- **与项目文件的重复检测。** 第一阶段只提供手动提升；是否自动提示「此记忆与 `AGENTS.md` 重复」由试用数据决定。

这些扩展不阻塞第一阶段。实施前必须满足的边界见「实施前必须保持的不变量」和「动手前的两项验证」。
