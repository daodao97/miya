# 自动化（Automations）

到了设定的时间，或者某个触发器发现条件满足（磁盘空间不足、外部脚本唤醒、文件变化、另一个自动化结束、电脑从睡眠中醒来），Miya 在指定项目里新开一个对话，用指定的 agent 发出一段固定的指令。唤醒机制见下文「唤醒」。设置了检查命令时，一轮结束后在项目目录执行它，没通过就把输出发回同一个对话继续下一轮，直到通过或轮数用完。运行结束后推送到手机。

界面原型在 [automations-ui.html](automations-ui.html)。

## 创建

以下方式都只需要一句话，例如「每个工作日早上 9 点看一下新 Issue，能修的修掉并保证 go test 通过，修不过就多试两次」。

- **Automations 页面**：写一句话，选项目和 agent。点击「整理设置」后，所选 agent 做一次不带工具的调用，按 JSON schema 回答名称、cron、检查命令、轮数和发给 agent 的指令（`internal/automation/draft.go`）。Claude Code 用 `-p --json-schema --output-format json --tools ''`，Codex 用 `exec --output-schema -o --sandbox read-only --ephemeral`。提示词里带上当前时间和项目顶层文件，用来推断检查命令，还带上当前可用的触发配方（见「条件」）。草稿里有条件时，Miya 先把它的命令试跑一次，结果显示在对应触发器下面；命令跑不起来时整理失败并给出原因。结果显示在「整理结果」里，每一项都能单独改。修改原话、项目或 agent 后，需要再次点击「整理设置」，新结果生成后才能保存。
- **手机端自动化页面**：点右上角「新建自动化」，选桌面项目和 agent，写一句话后点「整理设置」。桌面后台生成草稿，手机上可修改名称、运行时间、指令、检查命令、轮数、启用状态和是否带上上次结果。点「创建」后保存到同一个桌面后台，进入详情页；保存不会立即运行。运行时间按桌面端本地时区解释。整理期间仍可正常刷新自动化列表和使用其他手机功能。断线后保留表单；创建请求超时或断线时可以重试，同一请求即使已经保存或后台重启也不会重复创建。
- **对话里**：miya MCP 的 `create_automation` 由对话里的 agent 填好结构化字段。Miya 在这个对话里显示确认卡片，用户点「允许」才创建；10 分钟没处理按取消算。带条件时先在后台把条件的命令试跑一次：跑不起来就把原因直接返回给 agent 让它改，不弹卡片；通过后卡片上附带每个条件的试跑结果。`update_automation` 改开关时直接生效，改其他内容同样要确认，卡片显示改前和改后；只有这次调用给了触发器或策略时才试跑。`list_automations` 只读，Claude Code 不用确认就能调用。

Miya 用确定性代码校验 agent 的结果：cron 由 `internal/automation/cron.go` 解析，非法时报错；轮数限制在 1 到 5，没有检查命令时为 1；句子里有条件（「存储低于 5G 时」「下载目录有新文件时」）而没写时间时，生成对应的触发器、不设定时；既有时间又有条件（「每天 9 点，空间不足 5G 就清理」）时按时检查条件，满足才运行（Gate）；既没时间也没条件时暂定每天 9:00，并在界面上标黄；检查命令开头的 `cd <项目> &&` 会被去掉。

## 数据

一个自动化有名称、项目、agent、原话、指令、cron、检查命令、最多轮数和启用开关（`internal/automation/automation.go`）。全部存在服务数据目录的 `automations.json`，每个自动化保留最近 20 次运行：开始和结束时间、对话、第几轮、结果（运行中、通过、失败、已中断、已跳过）和一句话总结。

cron 是标准 5 段写法（分 时 日 月 周），按本地时间，支持 `*`、范围、列表、步长和英文缩写；日和星期同时指定时任一匹配即运行。常见写法会显示成中文，例如「工作日 9:00」「每周一、三 10:00」。

## 运行

调度器在后台服务里，每 15 秒检查一次（`internal/automation/runner.go`）。

- 到点后用 `submit` 在自动化的项目里新开对话，标题为「名称 · 日期」。项目不是当前打开的项目时，对话直接建在后台项目里，不切换窗口的项目。
- 上一次运行还没结束时，这次记为「已跳过」。
- 电脑睡眠或服务没运行而错过的时间，恢复后只补跑一次，记为补跑。
- 一轮结束的条件是对话不再忙碌、没有排队消息、也没有待处理的审批或提问。
- 检查命令在登录 shell 里执行，最长 10 分钟。没通过时把最后 4000 字输出发回同一个对话。
- 用户在对话里停止，或运行中关掉开关，记为「已中断」。
- 结束时推送一次「名称 · 结果（第 N/M 轮）」，自动化对话自己的「对话完成」推送不再发。运行中需要审批时，手机照常收到「需要你的确认」，Claude Code 的审批和后台项目的审批也包括在内。
- 服务重启时，上次没结束的运行记为「已中断」。

## 唤醒

自动化什么时候运行由「唤醒」决定。定时只是其中一种来源；所有来源产生同一种事件 `WakeEvent`，经过同一条管线后才开始运行（`internal/automation/wake.go`）。

```
触发源 ──WakeEvent──▶ 匹配 → 去重 → 防抖合并 → 冷却 / 每日上限 → 运行中跳过或排队 → Gate → 开始运行
```

一个自动化有可选的定时（`schedule`，可以为空）和若干触发器（`triggers`，任一命中即唤醒），以及一份唤醒策略（`policy`）。定时和「立即运行」不受冷却与每日上限限制，其余来源受限。

### 触发器

| 类型 | 何时唤醒 | 实现 |
| --- | --- | --- |
| `condition` | 一条命令说了算：命令成功（`success`）、输出变了（`changed`），或常驻命令打印了一行（`line`）。可以直接写命令，也可以用配方（`recipe` 加参数），见下文「条件」 | `success` 和 `changed` 默认每 5 分钟执行一次（`everyMinutes`），最长 30 秒；`line` 由 Miya 守护一个常驻进程。命令都在项目目录用登录 shell 执行 |
| `ingress` | 外部主动唤醒：`miya -wake` 或本机 HTTP | 见下文「外部唤醒」 |
| `file` | 文件或目录（不含子目录）的条目、大小或修改时间变化 | 每 15 秒比对一次快照，默认合并 30 秒内的变化；第一次只记录现状 |
| `after` | 另一个自动化的运行结束，可限定结果（`passed`/`failed`/`interrupted`） | 运行结束时触发，附上那次运行的结构化结果；不能跟随自己 |
| `system` | 电脑从睡眠中唤醒（`wake`） | 两次 Tick 之间墙上时钟跳过 2 分钟以上即判定为睡醒 |

#### 条件

Miya 不理解条件在测什么：一个条件就是一条命令，阈值、单位和比较都写在命令里。新的场景靠写一条命令或放一个配方文件来支持，不需要更新 Miya（`internal/automation/condition.go`、`recipe.go`、`stream.go`）。去重、防抖、冷却和每日上限仍由管线负责，命令不用管。

命令用 `$SHELL -lc` 在自动化的项目目录执行。`when` 决定怎么把命令变成唤醒：

- `success`（默认）：每 `everyMinutes` 分钟执行一次，最长 30 秒。退出码 0 算满足，1 算不满足，其他退出码或超时算探测出错，不算不满足。输出的第一行作为显示值，输出（最多 4000 字）作为数据交给 agent。
- `changed`：同样定期执行，输出和上次不同就唤醒，并把输出作为数据交给 agent，例如「有新 Issue 时分拣」「有新 tag 时写发布说明」。第一次只记录现状；输出的指纹保存在 `automations.json`，重启后不会为同一份输出再唤醒。命令失败算探测出错。它是事件而不是状态，没有「已触发 / 恢复」。
- `line`：常驻命令（`tail -F`、`fswatch`、消息队列的订阅端、自己写的监听脚本）。Miya 启动并守护它，标准输出每打印一个非空行就是一次唤醒，这一行作为数据交给 agent。

`changed` 和 `line` 不能用作 Gate。

常驻命令的守护规则：

- 触发器启用且服务在运行时进程才存在；关掉触发器、暂停或删除自动化、修改条件、服务退出时停止。进程在自己的进程组里，停止时先向整个组发 SIGTERM，2 秒后 SIGKILL，不留下子进程。
- 进程自己退出时重新启动，间隔从 5 秒起每次翻倍，最长 5 分钟；连续运行满 1 分钟后间隔复位。连续 3 次失败时推送一次提醒，错误信息取标准错误的最后一行。
- 每分钟最多接受 30 行，超出的丢弃并计数。
- 同一个触发器 5 秒内的多行合并成一次唤醒（可用 `debounceSeconds` 调整）。整理一句话生成 `line` 触发器时默认打开 `queue`，运行期间打印的行排队到结束后处理，而不是丢掉。

##### 配方

配方是别人写好的条件：一条带命名参数的命令，加一句说明。一个场景一个 JSON 文件，放进配方目录就多了一种触发器，不需要重启或更新；整理一句话的提示词和 MCP 工具说明每次都从目录里读取，所以 agent 立即能用上。

- 位置：数据目录下的 `triggers/`，正式安装是 `~/Library/Application Support/Miya/triggers/`。
- 内置的 `disk_free`（某个卷的可用空间低于若干 GB，用 `df`，不含 macOS 的可清除空间，数值会比 Finder 显示的小）和 `memory_free`（可用内存低于若干 GB；macOS 读 `vm_stat` 的空闲 + 非活跃 + 推测 + 可清除，Linux 读 `MemAvailable`）也是配方文件，在 `internal/automation/recipes/`，和用户的配方走同一条路径。配方目录里同名的文件会替换内置的。

```json
{
  "name": "disk_free",
  "description": "free disk space on a volume is below an amount, as in 'when storage is below 5G'",
  "when": "success",
  "command": "df -Pk \"$VOLUME\" | awk ...",
  "params": [
    {"name": "VOLUME", "description": "path of the volume", "default": "/"},
    {"name": "BELOW_GB", "description": "amount in GB, a number"}
  ],
  "text": "When free space on $VOLUME is below $BELOW_GB GB",
  "everyMinutes": 5
}
```

- `name`：小写字母、数字、`-`、`_`；不写时取文件名。`description` 告诉人和 agent 什么时候用它。
- `command` 必填；`when` 不写时为 `success`。
- `params`：参数以环境变量的形式传给命令。名字用大写（`BELOW_GB`），不能是 shell 自己要用的 `PATH`、`HOME`、`SHELL`、`USER`、`PWD`、`IFS`、`ENV`、`TMPDIR`。没有 `default` 的参数必须给值。
- `text`：界面上显示的一句话，`$NAME` 替换成参数值。`everyMinutes` 是条件没有自己指定时的执行间隔。
- 文件有问题（JSON 不合法、没有命令、名字或参数名不合规）时这个配方不可用，其他配方不受影响；新建页面会列出这些文件和原因。

条件引用配方时写 `{recipe: disk_free, params: {BELOW_GB: 5}}`。保存时配方的命令、`when` 和 `text` 被复制进条件：之后运行的就是确认时看到的那条命令，配方文件后来改了或删了都不影响已保存的自动化；要用上新版配方，重新保存这个条件。

旧写法 `{probe: disk_free, path: /, belowGB: 5}` 读入时自动转换成 `{recipe: disk_free, params: {VOLUME: /, BELOW_GB: 5}}`，并按新写法存回。换回不认识配方的旧版本时，旧版本读不懂新写法，会丢掉带条件的自动化。

##### 试跑

没人跑过的命令只是猜测，跑不起来的命令要等几天后才会以「探测出错」的形式暴露。所以条件在保存前先试跑一次（`internal/automation/trial.go`）：

- `success` 和 `changed`：执行一次，报告当前是否满足和显示值。当前不满足不算失败，探测出错才算。
- `line`：打印出一行，或保持运行 5 秒即通过；自己退出算失败。
- 整理一句话（桌面和手机）和对话里的 `create_automation` / `update_automation` 都会试跑，失败时不保存，原因返回给人或 agent。启用中的条件触发器和 Gate 都在试跑范围内，关闭的触发器不试跑。
- 页面上修改已整理草稿的其他字段、开关单个触发器不会重新试跑。

##### 触发与恢复

`success` 条件是边沿触发：满足时唤醒一次，并记为「已触发」；之后条件一直满足也不再重复唤醒，除非超过 `repeatHours`（默认 24 小时）。只要有一次探测不满足就恢复待命。Miya 不再知道数值和阈值，所以没有恢复余量：数值在阈值附近来回时，用 `cooldownMinutes` 限制，或者在命令里自己留余量。已触发的标记在唤醒进入管线之前就记下了，被冷却或每日上限暂缓的那次唤醒不会重试，要等条件恢复后再次满足，或超过 `repeatHours`。

运行进行中不执行 `success` 和 `changed` 的命令；运行结束后立即再探测一次，把结果记到这次运行上，详情页显示运行前后的值。连续 3 次探测出错时推送一次提醒。

### 唤醒策略

- `queue`：运行中又被唤醒时排队一个，结束后立即运行；后来的唤醒合并进这一个。不设时跳过，只记入唤醒记录，不占用运行历史。
- `debounceSeconds`：同一个触发器在窗口内的多次唤醒合并成一次，附带的数据拼在一起。
- `cooldownMinutes`：两次由触发器启动的运行之间的最短间隔。
- `maxPerDay`：24 小时内由触发器启动的运行上限，默认 24，用来兜底防止失控（例如两个自动化互相 `after`）。
- `gate`：一个 `success` 条件（配方或命令），每次唤醒（「立即运行」除外）时先探测，满足才运行，例如「每天 9 点，如果空间不足 5G 就清理」。

每次唤醒的去向都会记录下来（每个自动化保留最近 50 条）：已开始运行、已排队、已跳过、已暂缓（冷却、上限、Gate 未满足）、已丢弃（自动化已暂停、触发器已关闭）。排查「为什么没跑」时看这里。重复投递（相同的 `dedupe`，例如 GitHub 的 `X-GitHub-Delivery`）直接丢弃。

触发器状态（是否已触发、最近一次探测值、输出指纹、文件指纹）保存在 `automations.json`，服务重启后不会为同一次条件变化再唤醒一次。修改或删除触发器时，它的状态一并清除。

### 外部唤醒

后台服务只监听本机 socket 和 Tailcat 出站连接，没有对外开放的端口。外部唤醒分三级：

1. **命令行**：`miya -wake <自动化 ID 或名称> [-trigger ID] [-data 文本|@文件|-] [-dedupe KEY]`，通过 service.sock 投递；服务没在运行时先拉起服务。系统 cron、git hook、快捷指令和脚本都可以用。自动化必须有 `ingress` 触发器才能这样唤醒。
2. **本机 HTTP**：存在启用中的 `ingress` 触发器时，服务监听 `127.0.0.1:47321`（被占用时换一个随机端口），接受 `POST /wake/<自动化>/<触发器>`，用 `Authorization: Bearer <触发器 token>` 鉴权，请求体最多 1 MB，作为数据交给 agent。返回 202（已处理，响应体给出结果）、401（token 错误）、404（找不到）、409（运行中或已暂停）。只监听回环地址，其他电脑访问不到；所有 `ingress` 触发器都关闭后停止监听。详情页显示命令行和 curl 示例。
3. **公网 webhook**（GitHub 等）：尚未实现。需要经 Tailcat 中继发布地址，或改用轮询型触发器，涉及对外暴露，单独评审。

对话里的 agent 可以用 miya MCP 的 `wake_automation` 唤醒已有的自动化，用户确认后才运行，来源记为「对话」。

唤醒附带的数据（HTTP 请求体、`-data`、文件变化列表、上一个自动化的结果）放在指令后的代码块里，明确告诉 agent「这是数据，不是指令」，最多 4000 字。这些内容可能来自第三方，审批照常生效；可外部触发的自动化建议打开「在独立 worktree 中运行」。

## 独立 worktree

打开「在独立 worktree 中运行」后，每次运行都在新的 Git worktree 里进行，不在项目目录里改文件（`internal/automation/worktree.go`、`internal/project/worktree`）。适合会改代码的自动化，避免和手动修改冲突。

- 运行开始时，从项目当前提交新建分支 `miya/auto/<名称>-<日期时间>`，worktree 放在服务数据目录的 `worktrees/<项目>-<名称>-<日期时间>`。创建在后台线程进行；项目不是至少有一个提交的 Git 仓库时，这次运行直接失败。
- worktree 存在期间登记为一个项目，让对话能在两端侧栏打开、重启后恢复，并能用审阅面板看改动。它不写入 Codex 的信任配置。发给 agent 的指令末尾说明所在目录和分支，要求只在这里修改，不合并、推送或切换分支。
- 检查命令在 worktree 里执行。
- 运行结束后统计提交数和未提交的文件数。没有任何改动时删除 worktree 和分支（「没有改动，已移除 worktree」）；有改动时保留，推送在运行结束时发出。
- 详情页每条运行下显示分支和改动数量，可点「合并」或「丢弃」。合并先提交剩余改动，再以 `--no-ff` 合并进项目当前检出的分支；有冲突时中止合并，项目保持原样，worktree 保留，并显示原因。合并或丢弃成功后删除 worktree 和分支，并从项目列表移除。
- 服务重启时，上次没处理完的 worktree 重新统计一次，没有改动的照常清理。worktree 被手动删除时记为「已丢弃」。
- 手机端可以在新建时打开这个开关，并在运行历史里看到 worktree 状态和打开运行对话；合并和丢弃目前在桌面端进行。
- 对话里的 `create_automation` / `update_automation` 支持 `worktree` 参数，确认卡片显示「运行位置」。

## 后台服务

有启用的自动化时，后台服务不会因为没有窗口而空闲退出。同时在 `~/Library/LaunchAgents/com.daodao.miya.service.plist` 安装一个登录时启动服务的任务；没有启用的自动化时卸载。这个任务只负责启动服务，服务自己的单实例锁保证只有一个在运行；没有设 `KeepAlive`，应用更新时替换服务不会和它冲突。

## 界面

Automations 页面（`view_automations.go`）有三个画面：

- 列表：按 agent 着色的图标、名称、项目和完成标准、时间和下次运行、上次结果、开关、立即运行、打开上次对话。
- 新建和编辑：一句话输入框，项目和 agent 在输入框底栏；整理中显示骨架，失败可以重试。还没有整理结果时，输入框下方列出可用的配方（名称、说明、参数，自己添加的会标出）、配方目录，以及无法使用的配方文件和原因。配方由窗口直接读取，不经过后台服务。
- 详情：下次运行、最近通过次数、平均轮数、指令和设置、运行历史，每条历史可以打开对应对话。删除要点两次。

侧边栏里自动化发起的对话显示为时钟图标。界面不直接使用具体 agent 的名字，只通过 `agentBackend`。

手机端从侧栏的「自动化」进入，查看全部项目的执行计划、启用状态、运行历史和结构化结果，并打开对应的运行对话。列表右上角可新建自动化。详情页可点击「立即运行」，由桌面后台在对应项目中启动一次任务；暂停的自动化也可手动运行，不改变定时开关。请求提交期间和任务运行中禁用按钮，失败时显示具体原因。页面打开时按需读取，每 5 秒刷新；断线时保留本次已读取的内容。手机端和桌面后台均需更新；不支持新建或立即运行的旧后台会显示相应更新提示。断线或超时后不会自动重发运行请求，应先刷新确认是否已经启动。

## 已知限制

- 只在后台服务模式下运行，设置了 `MIYA_SERVICE=0` 时没有自动化。
- 默认在项目目录里直接运行，和手动发消息一样，可能和你正在做的修改冲突；打开「在独立 worktree 中运行」可以避免。
- 手机端自动化页面支持新建、查看和立即运行；编辑已有自动化仍需在桌面端进行，也可以在手机对话里描述操作。
- 整理一句话每次要等 15 秒左右，消耗少量额度。

## 以后可以加

| 功能 | 什么时候值得加 |
| --- | --- |
| 收件箱与「无事可报自动归档」 | 自动化多了，空结果的推送开始打扰人时 |
| 每次都继续同一个对话 | 需要跨天保持上下文的长期跟进 |
| 每个自动化单独设模型与推理强度 | 默认模型不合适时 |
| 公网 webhook（经 Tailcat 中继）、GitHub 等轮询型触发器 | 需要直接接收第三方服务事件时；本机 HTTP 与 `miya -wake` 已可用 |
| 桌面端编辑触发器的表单 | 需要在不重新整理一句话的情况下调整配方参数、命令或路径时；目前通过整理、对话或单个开关调整 |
| 手机端管理页 | 经常需要在手机上开关自动化时 |

## 运行结果

每次运行结束都会留下一份结构化结果，存在这次运行的记录里，和对话是否还在无关（`internal/automation/report.go`）。

- 运行时发出的消息是指令，加上一段说明：结束前调用 miya 的 `report_result` 工具上报 `summary`（总结）、`findings`（要点）、`metrics`（指标，含名称、数值、单位）、`artifacts`（产出文件或链接）、`needs_user`（是否需要人处理）。多次调用以最后一次为准；不是自动化运行的对话调用会报错。Claude Code 调用它不需要确认。
- agent 没有上报时，Miya 用对话最后一条回复和改过的文件生成自动摘要，并标明是自动摘要。
- 运行通过且有上报结果时，运行总结和推送内容使用上报的 `summary`。
- 「带上上次结果」开关默认打开：下次运行时附上最近一次有结果的运行的结构化结果，要求 agent 对比，指出新增、消失和变化较大的项。之前的对话删除了也不影响。
- 详情页每条运行下显示结构化结果，最近一次默认展开。

只保留最近 20 次运行。需要完整明细或长期趋势时，在指令里要求 agent 把每次结果写入项目里的文件。
