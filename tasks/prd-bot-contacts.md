# PRD：Bot 联系人

日期：2026-11-08  
状态：已实现；隔离回归、静态检查与五平台构建通过；真机手工验收未执行

## 1. 概述

在 Miya 中增加一组长期存在的 Bot 联系人。用户通过名字、头像、人设和擅长的事情认识它们，像打开 IM 联系人一样继续聊天。每个 Bot 可以用于日常聊天，也可以进入指定项目工作。

用户已明确选择：**全局联系人，兼顾日常聊天和项目工作。**

Bot 是独立于执行引擎和原生会话的产品对象。多个 Bot 可以使用同一个引擎；同一个 Bot 可以拥有日常会话和不同项目的会话。用户不必在每次新建聊天时重新输入人设或挑选模型。

首版保留现有项目入口，增加联系人入口。联系人页按“找谁聊”组织；项目页按“在哪工作”组织；两者打开同一份会话，不复制聊天记录。

## 2. 目标

- 从联系人列表一次点击即可打开该 Bot 最近的会话；没有历史时进入其日常聊天草稿。
- 新建 Bot 后可以完成首轮发送、退出重开和继续聊天，人设与会话归属保持一致。
- 同一个 Bot 可以分别在日常聊天、项目 A 和项目 B 工作，三个上下文独立。
- 桌面和手机读取同一后台中的联系人、会话关联、未读和执行状态。
- 既有未绑定 Bot 的项目会话继续可用，无需迁移到联系人后才能操作。

## 3. 产品模型与已采用的默认决策

### 联系人

每个 Bot 保存稳定 ID、名称、头像、简介、人设、默认引擎、默认模型和推理档位。名称与头像用于识别；简介用于解释擅长什么；人设用于约束表达方式、关注点和做事习惯。

人设不是权限配置。例如“果断的工程师”不会因此获得更宽的文件访问、命令执行或审批权限。联系人不拥有独立账号，默认复用 Miya 已配置的引擎账号，并在资料页说明当前执行引擎。

初始提供可选模板：“伙伴”“研究员”“工程师”。模板是可编辑的起点，选择创建后才成为联系人，不预先生成一批空聊天。允许从空白创建，允许多个联系人使用同一个引擎和模型。

### 会话

一个联系人可以有多段会话。点击联系人优先打开它最近一次使用、未归档的会话，保留该会话原有的日常或项目上下文；首次打开进入日常聊天草稿。页头明确显示“日常聊天”或项目名称，可切换已有会话、新建日常会话或在选定项目新建会话。

日常聊天使用后台数据目录下该 Bot 的独立工作目录，不继承当前打开的代码项目，也不将该目录登记为用户项目。这个目录只是执行工作目录，不能将其描述成文件系统隔离或沙箱。

项目会话仍属于原项目，并附带 Bot 身份。切换项目打开该 Bot 在目标项目最近的会话，没有则创建草稿；不修改当前原生会话的 cwd，不自动带入前一个项目的历史。

### 配置生效

名称、头像和简介修改后立即更新展示。人设、默认引擎、模型和推理档位修改后用于新会话；已有会话保留创建时的人设与执行配置，并显示“使用旧版人设”。用户可用最新配置新开会话。

会话内现有模型选择继续保留，只影响该会话；修改联系人默认模型不能静默切换已有会话。Bot 本身的身份不随模型或引擎变更而改变，但不承诺把旧引擎的原生上下文无损迁移到新引擎。

### 记忆

首版复用当前共享记忆，不新增一套自动提炼与向量检索系统。项目会话只召回该项目允许的记忆；日常会话只使用用户显式启用的用户级记忆，不因联系人最近进入过某个项目而加载该项目记忆。

不同 Bot 的会话历史默认不互相注入。用户级共享记忆仍可能被多个 Bot 读取，资料页与记忆入口说明这一点，首版不宣传“每个 Bot 拥有完全独立的长期记忆”。日常会话不把内部工作目录当成项目事实的默认记忆作用域。

### 多端与后台

联系人属于当前连接的 Miya 后台数据实例，在该实例的所有项目间可用。切换到另一台电脑时显示另一后台的联系人，不按同名联系人自动合并。桌面与手机均支持创建、编辑、聊天、选择项目和归档；运行仍由后台负责。

## 4. 用户故事

### US-001：创建与编辑联系人

作为用户，我希望创建一个有名字、人设和默认引擎的 Bot，以便以后直接找它聊天。

验收条件：

- [x] 可以从模板或空白创建，编辑名称、简介、人设、默认引擎、模型和推理档位。
- [x] 头像支持内置选择和本地图片；未选头像时使用名称首字与稳定底色。
- [x] 空名称不能保存；名称 1～40 字、简介不超过 120 字、人设不超过 8000 字，超限显示字段错误并保留输入。
- [x] 同名联系人可以创建，身份由稳定 ID 区分；同一引擎可以被多个 Bot 使用。
- [x] 保存失败保留表单；重复提交、超时重试和后台重启不产生重复联系人。
- [x] 重开应用后名称、人设、头像和默认配置完整恢复。
- [x] 验证桌面与手机的表单、校验提示和保存后状态，留存原生 UI 截图。

### US-002：像 IM 一样浏览联系人

作为用户，我希望一眼找到要联系的 Bot，并知道它有没有新消息或正在工作。

验收条件：

- [x] 全局导航增加“联系人”，保留“项目”和现有功能入口。
- [x] 列表展示头像、名称、最近消息摘要或简介、时间、未读与工作状态。
- [x] 按最近活动排序，支持置顶和按名称、简介搜索。
- [x] 一个 Bot 有多个会话时，工作状态与未读数按其会话聚合，打开一段会话不清除其他会话的未读。
- [x] 未启动 CLI 不显示为联系人离线；仅在发送不可用时显示具体引擎问题。
- [x] 已有用户升级后不被强制切离当前项目；没有联系人时显示创建入口和可选模板。
- [x] 验证桌面与手机空列表、长名称、多联系人、未读和并发工作状态的布局。

### US-003：日常聊天与续聊

作为用户，我希望点开联系人就能接着聊，不必先选择代码项目。

验收条件：

- [x] 首次点击进入该 Bot 的日常聊天草稿，不绑定当前代码项目；首条消息发送后建立原生会话。
- [x] 后续点击打开该 Bot 最近使用且未归档的会话，页头始终标明日常或项目上下文。
- [x] 可以新开日常会话，并从该 Bot 的会话列表切回旧会话。
- [x] 两个 Bot 使用同一引擎时，创建不同原生会话，人设与消息不串线。
- [x] 日常聊天继承现有附件、停止、排队、插话和审批能力；引擎缺失的能力按现有契约降级。
- [x] 后台重启后可以恢复联系人与原生会话的关联；恢复失败明确报错，不静默创建空会话代替。
- [x] 验证桌面与手机从联系人进入、发送、返回、重开续聊和引擎不可用状态。

### US-004：让同一个 Bot 进入项目工作

作为用户，我希望把熟悉的 Bot 带进项目，同时保持不同项目的聊天独立。

验收条件：

- [x] 聊天页可以选择已登记项目，打开该 Bot 在目标项目最近的未归档会话，没有则进入新草稿。
- [x] 日常、项目 A、项目 B 分别建立会话；来回切换恢复各自消息和草稿。
- [x] 发送使用页头所示会话的工作目录，不受其他窗口当前项目影响。
- [x] 项目会话在联系人和项目入口均可打开，停止、审批与未读指向同一份执行状态。
- [x] 项目选择不复制另一项目的历史、文件引用或项目记忆；用户仍可显式引用其他会话。
- [x] 删除或归档项目沿用原有项目语义，不删除联系人及其日常、其他项目会话。
- [x] 验证双端项目选择、上下文标签、跨项目切回及同一会话的双入口。

### US-005：人设稳定生效

作为用户，我希望 Bot 在新会话中保持设定的表达方式与工作习惯，并能知道修改何时生效。

验收条件：

- [x] 创建会话时冻结 Bot ID、人设版本、人设内容和执行默认值；重试与重连复用该版本。
- [x] 两个不同人设通过 fake CLI 验证收到各自配置；展示消息、复制和重发保留用户原文，不混入隐藏人设。
- [x] 人设由各 Adapter 通过已核验的原生配置或明确区分的上下文通道传递；不修改用户全局 CLI 配置与项目指令文件。
- [x] 修改名称、头像立即更新展示；修改人设后，旧会话显示旧版提示，可新开使用最新版人设的会话。
- [x] 正在运行的回合不因修改资料而中断或被替换配置。
- [x] 人设不改变审批模式、记忆作用域和工具能力；不能将人设当作用户对具体外部操作的授权。
- [x] 验证双端资料编辑、生效说明和旧版人设提示。

### US-006：联系人关联与历史可恢复

作为用户，我希望应用升级、引擎重新发现历史和后台重启后，仍能找到原来的 Bot 聊天。

验收条件：

- [x] 关联以后台来源、引擎和原生 session ID 为基础，不依赖窗口临时数字 ID。
- [x] 新会话尚未取得原生 ID 时使用持久化本地身份，取得原生 ID 后完成绑定，不重复建会话。
- [x] 原生历史重新发现后补回 Bot 关联、人设版本及会话上下文。
- [x] 对多个同引擎 Bot、不同项目、重启后 ID 变化均有隔离 fixture 回归。
- [x] 旧数据没有 Bot 字段时正常加载；旧客户端仍可将 Bot 会话作为普通原生会话打开。

### US-007：手机使用同一份联系人

作为用户，我希望离开电脑后，仍能在手机上找同一个 Bot 继续聊天或处理项目工作。

验收条件：

- [x] 联系人列表、资料、头像、会话归属、未读和工作状态来自所连接后台。
- [x] 手机支持创建、编辑、置顶、归档、日常聊天及选择项目，不自行启动 Agent 或写桌面数据文件。
- [x] 断线保留已加载内容与编辑草稿，发送不可用状态明确；恢复连接后重新核对服务端状态。
- [x] 修改请求具备稳定请求 ID，超时重试不重复创建或归档；两端同时修改同一资料时通过版本冲突阻止覆盖。
- [x] 旧后台缺少联系人能力时显示更新提示，现有项目聊天仍可使用。
- [x] 通过原生 fixture 验证手机窄屏、返回路径、长人设、断线和跨电脑切换。
- [ ] 真机手工验收：系统键盘弹出与图片选择器；本次没有安装到真机，未执行。

### US-008：归档联系人

作为用户，我希望移走不再常用的 Bot，并能找回其历史。

验收条件：

- [x] 归档后从普通列表隐藏，可在已归档联系人中恢复；归档不停止正在运行的任务。
- [x] 归档保留资料、头像、全部会话关联与人设快照，项目入口仍能打开对应会话。
- [x] 有新消息时按现有通知规则通知，不自动取消联系人归档；运行中仍可从全局活动找到任务。
- [x] 删除单段会话沿用现有会话操作，不删除联系人或其他会话；联系人永久删除不在首版提供。
- [x] 验证桌面与手机归档、恢复、仍在工作的联系人以及历史会话访问。

## 5. 功能要求

- FR-1：系统必须为每个 Bot 分配不随名称、模型和引擎变化的稳定 ID。
- FR-2：系统必须由后台服务持久化联系人资料。
- FR-3：系统必须允许多个 Bot 复用同一引擎账号。
- FR-4：系统必须在日常聊天发送前确定该 Bot 的独立工作目录。
- FR-5：系统必须将每个新会话绑定至明确的日常或项目上下文。
- FR-6：系统必须在创建会话时保存所用人设快照。
- FR-7：系统必须将隐藏人设与用户输入原文分开保存。
- FR-8：系统必须让联系人页与项目页引用同一个会话。
- FR-9：系统必须阻止当前窗口项目覆盖已选会话的执行目录。
- FR-10：系统必须按既有记忆权限与作用域召回内容。
- FR-11：系统必须向客户端提供联系人能力版本。
- FR-12：系统必须在所选引擎不可用时说明原因并保留输入。
- FR-13：系统必须在后台重启后恢复联系人与原生会话关联。
- FR-14：系统必须保持既有未绑定 Bot 会话的加载与操作兼容性。
- FR-15：系统必须将联系人归档与原生会话删除分别处理。
- FR-16：系统必须在资料修改版本冲突时返回可识别的冲突结果。

## 6. 首版不包含

- 多 Bot 群聊、自动互相发言、主持人调度，以及群聊内的角色路由。
- Bot 独占账号、独立虚拟机、容器或操作系统权限环境。
- 联系人之间自动共享完整聊天历史。
- Bot 级独立长期记忆、主动搭话和定时问候。
- 人设市场、云端联系人同步、多台电脑间联系人自动合并。
- 引擎切换后的原生会话迁移、修改历史会话的人设、批量重绑旧会话。
- 首版直接改造既有委派与自动化调度；未来可增加 Bot 作为目标，届时保留当前执行身份与通知语义。

## 7. 设计考虑

桌面采用“联系人 / 项目”两种入口，复用现有侧栏、活动区和聊天组件。联系人使用名称与头像作为主要识别，执行引擎与模型放在资料和聊天设置中。聊天页头明确给出 Bot 名称与当前上下文，项目标签可操作。

资料编辑器分为基本资料、人设和执行默认值。使用原生多行输入编辑人设，显示保存错误与配置生效说明。首版不要求用户配置 JSON 或提示词模板变量。

手机侧栏增加联系人入口，沿用当前聊天页与导航栈。发送前能直接看到日常或项目上下文。原生两端的截图与交互验证是 UI 验收依据；若实现中提供 Web 预览，UI 故事另需 Verify in a browser，Web 预览不能替代原生验收。

## 8. 技术考虑与现有代码接点

已检查的现有代码：

- `internal/ui/view_sidebar.go`：项目侧栏与线程入口，适合加入联系人导航。
- `internal/chat/model/model.go`、`types.go`：当前 Thread 与 SendRequest 尚未携带 Bot 身份和人设快照。
- `internal/controller/agent.go`：现有统一提交与 Agent Adapter 组合入口。
- `internal/agent/codex/send.go`、`internal/agent/claude/send.go`、`internal/agent/pi/`：原生发送、人设传递与恢复各自归 Adapter 负责。
- `internal/service/protocol/`、`internal/service/client/`：窗口与后台状态同步。
- `internal/phone/protocol/`、`internal/controller/phone_requests.go`：手机能力与业务请求入口。
- `internal/memory/`：现有项目级和用户级记忆；日常上下文需显式适配，不能简单将内部目录当项目。
- `docs/domain-scopes.md`、`docs/agent-adapters.md`：新增联系人领域遵循当前依赖边界，视图不解析原生协议。

建议新增独立联系人领域管理配置、版本与会话关联，由 controller 组装。后台单写者保存数据；窗口与手机通过现有服务发命令、读取投影。头像通过已有文件/附件通道按内容标识取用，不向手机暴露本机路径。

这份 PRD 不假定某个 CLI 参数已经可用。实施前核对各引擎实际版本支持的人设注入与恢复语义，再确定 Adapter 实现；不为了统一外观声明不存在的能力。日常工作目录与现有后台单实例、会话持久化、内存执行状态必须保持一致。

测试使用隔离数据目录与 fake CLI，不修改用户真实账号、项目、会话或已安装应用。多端协议增加可选字段，沿用既有版本兼容策略。

## 9. 成功标准与交付检查

- 三个 Bot 可以共享一个引擎完成独立对话；fake CLI 接收到对应人设和独立 session，恢复后关联不变。
- 同一个 Bot 在日常、项目 A、项目 B 完成发送与切回，工作目录、消息和项目记忆均符合所属上下文。
- 联系人创建、编辑与归档可在桌面和手机之间同步，超时重试不产生重复对象。
- 两端从联系人列表一次点击可继续最近会话，新建联系人无需代码项目即可发送。
- 现有项目会话、审批、排队、插话、未读和后台忙碌升级回归通过。
- 针对新增领域与恢复路径执行有意义的单元、契约、集成及竞态检查；执行仓库要求的静态检查与多平台构建。
- 实现验证和安装分别报告；本需求未授权安装或替换正在运行的后台。

## 10. 待评审事项

用户已确定全局联系人同时服务日常与项目工作。其余默认决策已在第 3 节给出，本稿无阻塞性技术选择。
